# Knee42 v13.1 Runnable Release Design

**Date:** 2026-08-26
**Public repair branch:** `fix/knee42-v13.1-runnable`
**Target release version:** `v1.0.1-v13.1` (remote publication is owned by Session C)
**Compatibility contract:** input `[1, 64, 438]`, 42 labels
**Non-goal:** modifying or replacing `v1.0.0-v13`

## Problem statement

The immutable `v1.0.0-v13` release is an accurately hashed five-file model-only release. It is not a runnable application bundle. The repository's published Windows entry and builder still launch the unrelated 27-class legacy runtime. A patch release must make Knee42 installable and verifiable from a clean directory while preserving the historical release, evaluation policy, and metric meanings.

The patch must not claim that a synthetic self-test proves recognition accuracy. The selected H Dev macro Top-1 remains 76.35%; the already-consumed J historical result remains 62.34%.

## Session A scope and handoff

Session A scope is limited to the v13.1 runtime, entry points, packaging, clocking, trigger behavior, and release verification. User-confirmed Phase 3 data decisions and new model creation/training belong to Session B and are not modified or revalidated by Session A.

Session C integrates Session B's new compatible 42-label [1, 64, 438] model. Session B supplies it as a model component directory, and Session C supplies that directory plus a caller-trusted component manifest SHA-256 to the release builder. Session C also owns remote publication. Session A makes the builder accept and verify that interface, but does not select, create, train, or alter the supplied model component. Because component identity is derived from the verified manifest, Session C can integrate Session B's new version without code edits.

Session A validates runtime and packaging only with the audited default component defined in Task 6 and assembled in Task 7, or the deterministic complete fixture component; Session C performs the first build with Session B's supplied release component.

“Audited default component” means only the complete deterministic assembly of the pinned old model ZIP plus the tracked `runtime_config.json` and `selection_ledger.json`, a generated internal `integrity_manifest.sha256`, the complete 42-label label map, all required model payload files, and the pinned `hand_landmarker.task` and `pose_landmarker.task`. The deterministic tiny complete fixture component mirrors the same layout and manifest contract for unit tests. Neither assembly is model selection or training.

## Considered approaches

1. **Commit all binary assets to Git.** Simple checkout, but adds model/task binaries to repository history, duplicates release assets, and makes later updates expensive.
2. **Ship only a network bootstrapper.** Small source archive, but not independently portable and weak under offline or clean-room verification.
3. **Build two artifacts from one staged manifest (selected).** Keep source, manifests, tests, and build scripts in Git. Download pinned assets into an explicit cache or accept an offline cache, verify every SHA-256, then produce a source-runtime ZIP and Windows portable ZIP from the same allowlist. Release assets contain all runtime files and third-party notices.

## Version and release boundaries

- `v1.0.0-v13` and its release assets remain untouched.
- The repair is `v1.0.1-v13.1`, described as the runnable v13 repair, not v14. Session A makes no model selection; the cross-session release integrates Session B's new compatible model through Session C.
- `packaging/knee42_ivcam/release_spec.json` is the canonical release specification. It declares release/app versions, `default_model_version: "v11"`, label count 42, input shape `[1, 64, 438]`, pinned assets, and layouts. The default value identifies only the audited historical default and never overwrites a supplied component's identity.
- A caller-trusted `component_manifest.json` declares `component_id`, `model_version`, `label_count`, `input_shape`, `payload_sha256`, `selection_ledger_sha256`, and `runtime_config_sha256`. The generated `VERSION_MANIFEST.json` derives `component_id` and `model_version` from that verified component, binds `model_component_manifest_sha256`, and accepts no separate caller override for label count, shape, or model version.
- Legacy 27-class entry points and documentation remain available only under an explicit legacy name/path. No formal v13.1 launcher may import them.

## Artifact architecture

The deterministic staging builder accepts a caller-supplied model component directory, the caller-trusted expected SHA-256 of `component_manifest.json`, a source commit, and a task-specific asset cache. The trust-anchor sidecar is held outside the component directory and its allowlist. The builder hashes the raw component-manifest bytes and compares that expected value before parsing or trusting any self-declared field. It then validates the component identity, 42-label `[1, 64, 438]` contract, internal integrity manifest, every payload hash, the selection-ledger hash, and the runtime-config hash. A recomputed trusted manifest cannot override label count or shape, while a verified compatible new model version becomes the generated identity. Staging is allowlist-based and fails on missing, changed, or unexpected required content.

The builder has an explicit online prepare/download-only mode. That mode reads pinned official URLs and SHA-256 hashes from the tracked specification, atomically populates and verifies the old model ZIP plus both versioned MediaPipe task assets in `$env:KNEE42_ASSET_CACHE`, and emits no release artifact. Every real offline fixture or release build runs only after this prepare gate and performs no network access. Session C may reuse the verified asset cache.

It produces:

- `Knee42-v13.1-source-runtime.zip`: Python source subset, the verified complete component under build, the single trigger config and provenance, requirements lock, launch/setup scripts, licenses, model card, golden contract, release manifest, and checksums.
- `Knee42-v13.1-windows-x64.zip`: an onedir PyInstaller application built from the same staging tree and manifest, with a Knee42-only entry, complete assets, licenses, self-test, and checksums.

Every archive contains a root integrity manifest. The model component directory retains its internal manifest. The root manifest binds `component_id`, `model_version`, the caller-trusted component-manifest SHA-256, all component members and payload hashes, the complete label map, both `.task` files, trigger config/provenance, source layout, golden contract, dependency lock, notices, and version manifest. The release directory contains `SHA256SUMS.txt` over distributable artifacts and a machine-readable build report. ZIP member ordering and timestamps are normalized.

The runtime performs no network access. Missing or tampered files fail before detector/model construction and identify the affected path.

## Runtime contracts

### Clocking

- Camera/live input uses elapsed `time.perf_counter()` from source start. Nominal reported FPS is display metadata only.
- Video replay uses the source container timestamp (`CAP_PROP_POS_MSEC`) for each decoded frame. A documented deterministic fallback is permitted only when the backend reports no usable timestamp; the selected mode is logged.
- Held observations for `frame_step=2` are assigned the actual collected timestamps, never invented future timestamps.
- Timestamps must be finite and monotonic. Regression fails closed with a clear error.

### Orientation and handedness

- `--rotation {auto,0,90,180,270}` and `--input-mirror {off,on}` are explicit CLI/config values. Display mirror is independent and never changes model features.
- The runtime declares whether MediaPipe handedness labels require swapping for the supplied pixel orientation. The mapping is centralized.
- Anatomical golden frames verify pose left/right indices and hand slots using asymmetric landmarks. Tests do not infer anatomy from screen position.
- Input/display transforms do not imply any Phase 3 training or data change; those decisions remain outside Session A scope.

### Probability display

- Knee42 exposes raw softmax probability and labels it `raw_probability` / "raw probability".
- No accept/reject threshold is enabled because the release has no held-out calibration or risk-coverage artifact.
- The legacy confidence inflation curve is disabled/identity-marked in the isolated legacy runtime so it cannot be mistaken for calibrated probability.

### Trigger and boundary evidence

- The application loads exactly one trigger config from the staged bundle; no fallback config or CLI override is accepted in the formal launcher.
- Root integrity plus provenance bind the config, controller source, relevant runtime source, model, selection ledger, build source commit, and boundary policy.
- Startup validates threshold ordering and start/blank/hold/rest/time constraints.
- Per-segment telemetry records clock mode, orientation, config/provenance hashes, start/end/decision timestamps, reason, threshold state, and any calibration-block reason.
- A PII-free annotated synthetic replay corpus covers nominal segmentation, premature-cut resistance, two-segment merge resistance, expected max-duration timeout, and boundary error. The gate reports segment recall, premature cuts, merges, unexpected timeouts, and boundary error; it cannot pass merely by swapping two thresholds.

### Startup and self-test

Startup emits structured JSON with entry module, release/app/model versions, `component_id`, the 42 labels, input shape `[1,64,438]`, full root/model/task/config/provenance SHA-256 values, clock mode, rotation, input/display mirror, and resolved trigger config. It obtains `component_id` and `model_version` only from the generated, integrity-verified `VERSION_MANIFEST.json`, displays both before detector/model construction, and never trusts command-line or unverified component values.

Self-test performs:

1. root and internal integrity verification;
2. real MediaPipe task construction;
3. deterministic golden landmark-to-tensor materialization;
4. real CPU model forward;
5. exact tensor and logits checksum comparison;
6. 42-logit/label contract validation.

The golden fixture is a software-contract check, not a semantic clip or accuracy estimate.

## Dependencies, licensing, and clean installation

- Python 3.10 x64 is the supported release interpreter. Before Task 1, the caller must set `$env:KNEE42_PYTHON` to an existing interpreter file; preflight invokes that exact path and rejects every version other than Python 3.10 or every non-64-bit interpreter. PATH-based interpreter discovery is not allowed.
- `requirements-windows-build.lock.txt` contains the complete runtime closure plus build-only dependencies. A fresh build environment installs it before the full suite and every artifact build.
- A separate fresh runtime-only environment installs only the `requirements-windows-runtime.lock.txt` taken from the integrity-verified clean extraction and independently tests that extracted source runtime and self-test. Builder packages are not installed in that environment.
- Build preflight verifies Python architecture and imports of Torch, MediaPipe, OpenCV, NumPy, and Pillow.
- MediaPipe Hand Landmarker v1 and Pose Landmarker Lite v1 are fetched from versioned official URLs and pinned by SHA-256. Their official model cards state Apache-2.0; the artifact includes the license/model-card attribution and notices.
- Model licensing, application licensing, direct dependencies, builder dependencies, and bundled license texts are separated clearly. A component inventory/SBOM is emitted.

## Test and release gates

Implementation follows red-green-refactor. Session A exercises the runtime, packaging, and verification mechanics with a deterministic compatible test component. The release gate requires fresh evidence for:

- all Session A public unit and integration tests;
- clock, handedness, raw probability, trigger replay, telemetry, startup, and fail-closed tests;
- exact archive members, deterministic rebuild, checksums, licenses, source layout, and provenance;
- clean extraction/install and `--self-test` in a fresh Python 3.10 environment, first with the Session A test fixture and then with the Session C release component;
- deterministic golden tensor/logits checksums generated and verified for the component under test;
- formal Windows entry imports/runs Knee42 and contains exactly 42 labels;
- short headless timestamped video replay;
- source and release scans for credentials, personal/absolute paths, raw media, and unnecessary large files.

For the Git secret scan, exit 1 means clean, exit 0 means findings and failure, and every other nonzero exit means the scan command failed. Secret sentinels are assembled from split literals so the scanner does not match its own definitions. Documentation tests parse executable code fences and reject bare `python`, `python3`, `python3.10`, and `py -3.10`; normalize ordinary and multiline prose when enforcing Session B training ownership; inspect complete continued output commands for literal repository-relative build paths; limit angle-placeholder checks to executable fences; and enumerate every real asset-prepare and offline artifact command when enforcing order.

Session A creates and verifies its final clean commit before the final artifact/evidence build, records that exact HEAD as `$env:KNEE42_FINAL_HEAD`, and writes only ignored or out-of-tree outputs afterward. No tracked file change or commit is permitted after the final build starts. `VERSION_MANIFEST.source_commit` and `handoff_record.source_commit` must both equal the recorded final HEAD. Session A hands that clean local branch/commit and the exact environment-variable-based builder command to Session C. Session C integrates the supplied compatible model component, runs every component-dependent build/self-test/golden gate, performs remote branch/PR/tag/release publication, and records the integration and publication evidence.
